Blueprint upload

Select the original workbook and upload. The server discovers the header and worksheet layout, extracts identity and version, validates the blueprint structure, and writes only after automatic checks. No preview or metadata form is required.

Identity, version, and blueprint intent must be established from the file; missing or contradictory fields produce actionable errors rather than invented values. Missing lifecycle defaults to Draft. Existing records are not overwritten; version conflicts are reported.

        Row-level validation and database report

            Duplicates and accounting: repeated Full Question ID values within this file are reported separately from IDs already in the database. The result distinguishes validation passes/rejects from database attempted, inserted, failed, and unknown writes; a retry is insert-only and does not create another question version.
            Required content: each accepted question needs an ID, stem, positive marks, board, class, subject, chapter, topic, supported difficulty, question type, answer, and source paper. Fractional marks are accepted to three decimal places. Missing/placeholder fields, malformed options or structure, likely encoding corruption, explicit negative-selection wording, and detected truncation remain quality-gate failures; valid negative numbers and mathematical notation remain allowed. Genuine defects are not auto-corrected or silently discarded.
            Structured metadata contract: structure_type is descriptive free text (use subject-specific labels; there is no exhaustive global enum). content_features is an array of descriptive strings; delimited input may use semicolon, comma, pipe, or newline, while a JSON string array is safest when a feature itself contains a delimiter. Values are stored as PostgreSQL TEXT[].
            structure_data contract: stored as a JSONB object. Legacy prose is accepted as {"kind":"description","description":"…"}. For multipart questions, use {"parts":[{"label":"a","marks":1.5}],"internal_choice":false}; labels must be unique, marks positive (≤3 decimals), and when there is no internal choice their sum must equal the question marks. Internal-choice parts require choice_groups metadata. No parts schema is inferred from unrelated fields.
            Actionable errors: expand “Row-level validation and database report” to see file, worksheet, spreadsheet row, question ID, field, and repair guidance; download the JSON report to fix and revalidate the source rows. Detected truncation details are also listed separately and stored with rejected rows.
            Excel tip: only the first sheet is read for question uploads. Column names are flexible (QID, Question Text, Type… all work).

            Blueprint path: The original JSON, CSV, or XLSX file is sent as multipart binary directly to the authenticated n8n webhook and parsed server-side; the browser does not convert it into a Blueprint JSON model. All XLSX worksheets and source columns are inspected; unknown fields and unsupported worksheets are preserved and reported. A master curriculum sheet with Chapter_No, Chapter_Name, and Unit_Domain produces a separate distinct chapter pool while every subtopic row remains a slot; a dedicated Chapter_Pool sheet takes precedence. No chapter-level target weights are inferred from row marks. Complete-paper intent is used only when explicitly declared in the file; no fixed slot/mark targets are inferred from an ID or workbook title. CSV supports nested choices, subparts, rules, section definitions, and a chapter pool only when represented as JSON cells. Missing section definitions are clearly marked as derived from slots. Missing subject references remain null; the uploader never creates reference rows.
            Access control: The n8n Webhook enforces its dedicated Basic Auth credential before the workflow runs. This page does not contain the password; it sends credentials entered by an authorized user over HTTPS. The webhook CORS allow-list must contain only the exact HTTPS origin serving this page. CORS is not authentication, and the uploader name is an audit label, not identity proof.
            Version safety: identity, version, lifecycle, and complete-paper intent are read from the uploaded file; missing lifecycle defaults to DRAFT. Automatic validation and conflict checks run before any write. Existing records are never overwritten or retired by this uploader; publishing is blocked when a published sibling exists. The direct authenticated request reaches one unified workflow; its upload-type router selects the Blueprint branch.
